# How hassette-codegen Works

## Overview

Hassette needs typed Pydantic state models and typed entity command wrappers for every Home Assistant entity domain (light, climate, fan, sensor, and so on) — hand-writing and maintaining ~40 of these by hand against a moving upstream target would be a constant drift risk. `hassette-codegen` (a standalone package at `codegen/`, separate from the main `hassette` package) closes that gap by reading Home Assistant core's own Python source directly — the entity class definitions, the `services.yaml` service schemas, the `const.py` enums — and generating the Pydantic models and service-call wrappers hassette ships from that source of truth. It runs as a CLI (`hassette-codegen generate`), is pinned to a specific HA release in CI (`codegen/ha-version.txt`), and is safe to rerun repeatedly against an evolving upstream: unrecognized or hand-written files are never clobbered, broken output is never committed, and a `--check` mode lets CI detect drift without touching the tree.

## Components and Their Responsibilities

**`pipeline.py`** is the orchestrator. `run_pipeline()` is the top-level entry point that runs domain discovery, drives extraction and generation for every domain, and finalizes the manifest. It also owns the two guard rails that keep generation from ever touching hand-written code (`RESERVED_BASENAMES`, `_may_overwrite()`) and the domain-name validation that rejects unsafe or reserved domain names before anything else runs.

**`ha_source.py`** resolves *where* Home Assistant's source comes from — either a local checkout path or a shallow git clone of a release tag — and discovers which components under `homeassistant/components/` actually define an entity domain (detected by a marker string, `CACHED_PROPERTIES_WITH_ATTR_`, plus an AST check for an entity class). It owns cleanup of any temp clone.

**`extractors/`** is where AST parsing of HA source happens. Each extractor has a narrow job: `properties.py` reads `_attr_*` annotated fields off the entity class to become Pydantic fields; `features.py` reads both `IntFlag` (`*EntityFeature`) and `StrEnum` classes out of `const.py`/`__init__.py`; `base_class.py` applies a small heuristic (toggle → bool state, numeric `state` property → numeric state, otherwise string state) to pick which Pydantic base class a domain's state model inherits; `services.py` reads `services.yaml` plus cross-references the entity's `__init__.py` for the actual async method names, resolving Home Assistant's `[%key:...%]` translation-string references along the way; `constants.py` pulls sensor device classes, state classes, and unit enums for a separate generated constants module.

**`overrides.py`** plus the TOML files under `overrides/` is the escape hatch for everything the heuristics get wrong. A `DomainOverride` per domain can rename or retype a field, add or remove a property outright, force a specific base class, or declare a domain's properties by hand entirely (`discovery = "manual"`, bypassing AST extraction). Overrides are applied as a distinct step *after* extraction — extraction never knows overrides exist, which keeps the two concerns cleanly separated and makes the override's effect traceable (extracted-then-overridden, not tangled together).

**`domain_data.py`** defines `ExtractedDomain`, the single dataclass that all the extractor outputs get assembled into per domain — this is the boundary object handed to the code generators.

**`generators/states.py`** and **`generators/entities.py`** turn an `ExtractedDomain` into rendered Python source, via Jinja2 templates (`templates/state_model.py.j2`, `templates/entity_wrapper.py.j2`) loaded through a shared environment (`generators/_env.py`). `states.py` also handles enum name normalization (aligning inconsistent HA naming like `FanStateAttribute` to a canonical `FanEntityStateAttribute`, and renaming a `StrEnum` that would collide with the generated Pydantic class name). `entities.py` maps `services.yaml` selector shapes to Python types (`type_mapping.py`), matches string-literal parameters back to a domain's own `StrEnum`s so generated signatures use named enums instead of bare `Literal[...]` where possible, and builds Google-style docstrings from HA's service descriptions.

**`sync_facade/`** is a second, unrelated code-generation path that generates synchronous wrapper classes so app code can call async framework APIs from a worker thread. It has two distinct sub-mechanisms, not one: `generators/generic.py` extracts just the *signature* of each public async method on `Api`, `Bus`, `Scheduler`, and `HelperClient` and emits a thin delegate method that calls `self.task_bucket.run_sync(self.<wrapped_attr>.<name>(...))` — the original method *body* is never copied, only re-derived from its signature. Separately, `sync_facade/recording_transform.py` generates `RecordingSyncFacade` by AST body-copying the hand-written `RecordingApi`/`RecordingHelperClient` test doubles (`src/hassette/testing/recording_api.py`) — rewriting `self.X` → `self._parent.X` and stripping `await` — because that test double's methods contain real logic (not just a passthrough call) that needs to be preserved verbatim in sync form.

**`rendering.py`** is the safety layer all template output funnels through: `py_literal` for safely emitting arbitrary strings/ints as Python source, `escape_docstring_text` for neutralizing triple-quote breakouts in HA-authored descriptions, and `require_identifier` for rejecting anything that isn't a valid, non-keyword Python identifier before it lands in a method or parameter name position.

**`output.py`** is the last stage before anything touches disk: `atomic_write()` formats and lints generated content with `ruff`, validates it compiles (`py_compile`), and only then atomically replaces the target file — a failure at any validation step leaves the previous file untouched. `check_drift()`/`format_via_ruff()` provide the equivalent read-only comparison used by `--check` mode.

**`manifest.py`** tracks file ownership across runs via `.generated-manifest` at the repo root — the record of which files this tool is allowed to overwrite.

**`__main__.py`** is the CLI surface: `generate` (the main pipeline) and `sync-facade` (the Api/Bus/Scheduler/Helpers/Recording facade path) subcommands, both supporting `--check`.

## The Flow

A run starts by resolving where Home Assistant's source lives — either a path the caller already has checked out, or a fresh shallow clone of a release tag — and scanning it for every component directory that looks like an entity domain. In parallel, the tool loads whatever TOML overrides exist under `overrides/`, and warns if an override file doesn't match any discovered domain (a signal the domain was renamed or removed upstream).

Domain names are validated up front, before any extraction happens: names that collide with a small set of reserved basenames (`base`, `catalog`, `input`, `simple`, `__init__` — all names of hand-written support modules the generator must never touch) or that aren't valid Python identifiers are rejected outright and excluded from generation, independent of whatever the manifest says.

For each surviving domain, extraction runs domain-by-domain: pull the `IntFlag` feature classes, the `StrEnum` classes, the `_attr_*` property fields, infer (or take from an override) the base state class, and — if a `services.yaml` exists — extract the service definitions with their field types and resolved descriptions. If the domain declared `discovery = "manual"` in its override, this whole AST-extraction step is skipped and the override's hand-declared property list is used instead. Whatever comes out is then run through property overrides (rename, retype, add, remove) before being packaged into one `ExtractedDomain` per domain.

Generation takes that `ExtractedDomain` and produces two files: a state model (normalizing enum names, resolving HA-internal types like `dt.datetime` to hassette's `whenever`-based equivalents, then rendering through a Jinja template) and an entity wrapper (mapping each service's selector types to Python types, matching parameters back to the domain's own enums where the values line up, promoting repeated `Literal[...]` shapes to named type aliases, building docstrings, then rendering through a second template). Every free-text value that HA supplied — enum member values, service names, descriptions — passes through the `rendering.py` safety functions before it becomes part of generated Python source; a service or parameter name that fails identifier validation drops that domain's *entity wrapper* entirely (the state model, if already generated, still ships) rather than emit broken syntax.

Before either file is actually written, a manifest-ownership check (`_may_overwrite()`) decides whether the tool is allowed to touch that path: a file that doesn't exist yet is always fine to create; a file that exists but the manifest doesn't yet track (fresh checkout, generator has never run) gets a free pass; a file the manifest tracks and lists as owned is fine to regenerate; a file the manifest tracks but does *not* list as owned is refused — the domain is skipped for that file rather than clobbering something hand-written. Once cleared to write, `atomic_write()` runs `ruff format`, `ruff check --fix`, and `py_compile` against a temp file in the target directory, and only replaces the real file if all three pass; if anything fails, the previous version stays on disk untouched and the write does not count toward this run's generated-files set.

After every domain has been processed, the pipeline generates the shared sensor-constants module, runs a freshness check (`--check` mode only) comparing HA's ported `_numeric_state_expected` predicate source against a committed snapshot — because hassette hand-ported that specific piece of logic rather than generating it, and this is the only mechanism that would notice upstream silently changing it — regenerates the `states/__init__.py` and `entities/__init__.py` package inits, and, outside `--check` mode, finalizes the manifest: either a straight overwrite with everything this run generated, or (if `--domain` filtered the run to a subset) a merge that preserves manifest entries for domains that weren't processed this time, so a partial run never causes unrelated, un-regenerated domains to be flagged as orphaned in the next run.

`--check` mode runs the identical extraction/generation logic but never writes: it normalizes both the committed file and the freshly generated content through the same `ruff` formatting pass and compares them, reporting a diff on mismatch. It never touches the manifest or the filesystem, which is what makes it safe to run in CI on every push without a risk of the check itself introducing drift.

## Key Decisions and Invariants

**Extraction and override are strictly staged, never interleaved.** Extractors only ever read HA source; they have no knowledge that overrides exist. Overrides are applied as a distinct post-processing pass over the extracted result. This means a property's provenance is always traceable: "what did HA's source say" and "what did we deliberately change" are two separate, inspectable steps rather than one heuristic doing both at once.

**Two independent write-protection layers, because they cover two different points in time.** `RESERVED_BASENAMES` protects hand-written modules on a fresh checkout, before any manifest exists at all — without it, a first run against a repo with no manifest would treat "file doesn't exist yet, or manifest doesn't track it" as blanket permission to write, and could clobber `base.py`/`catalog.py`/etc. if HA ever happened to name a component the same thing. `_may_overwrite()`'s manifest-ownership check protects everything else on every subsequent run. Neither layer alone is sufficient; both must hold for the guarantee "the generator never overwrites hand-written code" to be true.

**A failed write never claims ownership.** `atomic_write()` only adds a path to the generated-files set if formatting, linting, and compilation all succeeded. This is what makes the manifest self-healing: a domain whose generated code happens to be invalid Python (e.g., an unresolvable HA type) simply doesn't get its file touched or claimed this run, and orphan detection on the next full run will flag it rather than silently leaving a stale or broken file in place unnoticed.

**`--domain` filtering requires a manifest merge, not a manifest replace.** If a filtered run just overwrote the manifest with only the domains it processed, the next unfiltered run would see every other domain's files as "in the old manifest but not the new set" and report them as orphaned — even though they're legitimately still generator-owned, just not touched this run. `merge_manifest()` exists specifically to make incremental, per-domain regeneration safe.

**Rendering safety is per-value, not blanket.** The Jinja environment disables autoescaping deliberately (HTML escaping would corrupt Python string literals), so every place HA-supplied free text reaches the template — enum values, service names, docstring text — goes through one of three explicit functions (`py_literal`, `escape_docstring_text`, `require_identifier`) rather than relying on template-engine escaping to make untrusted input safe to embed as source code.

**The freshness-predicate check is narrow by design.** It exists only to catch HA changing the *upstream* logic behind a specific piece of hand-ported code (`_numeric_state_expected`) that codegen does not itself generate — it is not a general drift detector, and only runs in `--check` mode against domains where a `sensor` component exists in the source being checked.

**Two unrelated codegen strategies coexist for a reason, and that reason is also a maintenance risk (tracked as issue #938).** Entity wrappers are template-driven because they come from structured YAML data — templates are the natural fit. Sync facades (`sync_facade/`) are generated by re-deriving a method's signature from the hand-written async implementation and emitting a fixed `self.task_bucket.run_sync(...)` delegate call, rather than rendering a template — because the delegate body is always the same shape, only the signature varies per method. The cost is that a cross-cutting change to sync dispatch behavior (new timeout, added telemetry) has to be made correctly in both `entities.py`'s `call_service()` path and `sync_facade/`'s `task_bucket.run_sync()` path, or the two diverge silently.

## Boundaries

**What this subsystem expects from its inputs:** a Home Assistant core checkout (local or a resolvable git tag) whose `homeassistant/components/<domain>/` layout, entity-class shape (`_attr_*` fields, `ToggleEntity`/`Entity`/`RestoreEntity` inheritance), and `services.yaml`/`strings.json` conventions match what the extractors expect. The extractors are AST-based and pattern-based, not schema-validated against an HA-published contract — if HA restructures how entities declare state or services, extraction silently produces less (or wrong) data rather than failing loudly, which is part of why the freshness check and CI's pinned-version `codegen-freshness` job exist as a backstop.

**What this subsystem hands back to hassette:** generated Python source files under hassette's `src/hassette/models/states/` and equivalent entity-wrapper locations, tracked via `.generated-manifest` at the repo root as the ownership record consumed by future runs. It does not import or depend on the main `hassette` package — it's a fully separate `pyproject.toml`/dependency set (`jinja2`, `pyyaml`) whose only integration point with the monorepo is the files it writes and the manifest it maintains.

**What callers (CI, developers) are responsible for:** invoking `--check` mode to detect drift without side effects, keeping `codegen/ha-version.txt` pinned to a known-good HA release for CI reproducibility, and — when the freshness check or a rejected domain surfaces a real upstream change — either updating an override in `overrides/*.toml` or (for the ported numeric-state predicate) refreshing the committed snapshot after manually re-verifying the ported logic still matches. The tool will not silently paper over an upstream change; it is built to stop and report rather than guess.
