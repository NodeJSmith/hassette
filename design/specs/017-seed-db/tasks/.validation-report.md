## Warnings

- **T01 Verify items for FR#3 and FR#4 don't verify the FR text they're tagged with.** Design FR#3 is "each scenario produces a complete dataset across all 6 telemetry tables" and FR#4 is "all data within a scenario is referentially consistent (FK values point to real rows)." T01's Verify criteria for these two identifiers actually check something else entirely — that the renamed param builder functions are importable, and that `job_insert_params` hardcodes `repeat=0`. Those are legitimate things to verify, but they are not FR#3 or FR#4 as defined in the design doc; they're prerequisites for later tasks (T02/T03) to satisfy FR#3/FR#4. Recommend either dropping FR#3/FR#4 from T01's `implements` field (T01 is really laying groundwork, not implementing the requirement) or rewording T01's Verify bullets so they don't read as if they close out FR#3/FR#4 on their own — a reader scanning only T01 would wrongly conclude FR#3/FR#4 are fully satisfied by this task.

- **FR#4 ("referential consistency") has no Verify item anywhere that checks the requirement as stated.** T01's FR#4 item checks param-dict correctness (see above); T02's FR#4 item checks that `SeedContext` tracks IDs across tables, which is necessary infrastructure but doesn't itself assert that inserted FK columns hold valid values. The actual guarantee of referential consistency comes from the FR#6 (`PRAGMA foreign_key_check`) and FR#7 (LEFT JOIN consistency assertion) mechanisms, and is exercised end-to-end by AC#3/AC#4 in T04. This is not a coverage gap by the strict rule (every claimed identifier has *a* Verify bullet), but a reader relying on the FR#4 traceability row alone would not find a bullet that actually re-derives "FK values point to real rows" — that assurance is implicit, spread across FR#6/FR#7/AC#3/AC#4 instead.

- **T02's FR#10 Verify item is a degenerate/trivial case.** "scenario_empty uses no app keys (zero rows in all tables)" technically satisfies "fictional app keys" only because there are zero app keys to check. The substantive verification of FR#10 (fictional keys not colliding with `examples/`) lives in T03's Verify item, which is fine given the matrix allows multi-task coverage — but a reviewer scanning T02 in isolation may be misled into thinking FR#10 is meaningfully verified there.

- **T02's `insert_row` helper description in Prompt omits `blocking_events` when describing tables without `RETURNING`.** The design doc's Architecture § "Write path" explicitly states: "For tables without RETURNING (log_records, blocking_events — no integer PK returned), the helper returns `cursor.lastrowid`." T02's Prompt narrows this to "For tables without RETURNING (log_records), return `cursor.lastrowid`" — dropping `blocking_events` from the sentence. This is likely inconsequential in practice (the `SeedContext.add_blocking_event` signature returns `None`, so no ID is tracked either way), but it's an incomplete restatement of a design fact and could cause an implementer to assume `blocking_events` inserts use `RETURNING id` when they don't.

If the executor takes this path, AC#6 will ship without automated verification — worth flagging to the user before execution so a skip isn't silently accepted as "done."
