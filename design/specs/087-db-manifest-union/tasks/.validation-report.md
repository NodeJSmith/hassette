## 5. Additional Findings (Outside Strict Traceability Scope)

These do not affect the PASS verdict per the stated rubric (which is scoped to FR/AC coverage, contradictions with the design doc, non-local criteria, and context.md completeness), but were surfaced by independently reading the actual codebase and are worth fixing before implementation:

1. **T01 Focus section references a nonexistent `HEAD_VERSION` constant.** T01 says: "Check `src/hassette/core/database_service.py` for the `HEAD_VERSION` constant that tracks the expected schema version — it must be bumped to 11." No such constant exists anywhere in `src/hassette/` (confirmed via repo-wide grep). Schema version is instead derived automatically from the migration filename: `migration_runner.py:_apply_migration()` appends `PRAGMA user_version = {version}` itself (where `version` comes from parsing the numeric filename stem), and `_collect_migrations()` globs `*.sql` files by stem. **T01's instruction to manually add `PRAGMA user_version = 11;` inside `011.sql` is also unnecessary/risky** — the runner already appends this statement after the migration's SQL content; a hand-written duplicate PRAGMA in the file would either be redundant or (if placed before `COMMIT`) harmless but confusing. Recommend removing both the `HEAD_VERSION` reference and the manual `PRAGMA user_version` instruction from T01's Prompt/Focus, replacing with "no manual version bump needed — the runner derives the version from the filename `011.sql`."

2. **T02 Focus section's repository-access hint doesn't match the actual convention.** T02 says: "Access to the repository: `self.hassette.database_service.repository.upsert_app_manifest(manifest)` or however the repo is accessed in this codebase" (appropriately hedged, but the specific path shown is wrong). In the actual codebase, `TelemetryRepository` is owned by `CommandExecutor` (`command_executor.py:166: self.repository = TelemetryRepository(hassette.database_service)`), not by `DatabaseService`. Existing callers reach it through `self.hassette.command_executor` — e.g. `bus_service.py:204: db_id = await self._executor.register_listener(reg)`, and `app_lifecycle_service.py:660: await self.hassette.command_executor.reconcile_registrations(...)` (this file already uses this exact access pattern elsewhere). Neither design.md nor T02 mentions `CommandExecutor` at all, despite it being the established layer for exactly this kind of repository write. Recommend T02 be updated to route the manifest upsert through `self.hassette.command_executor` (possibly adding a `register_app_manifest()`-style method there, paralleling `register_listener`/`register_job`) rather than a direct `database_service.submit(repository.method())` call.

Both findings are implementation-detail risks that could cost an implementer time (chasing a nonexistent constant, or writing code that bypasses the established `CommandExecutor` convention) but are correctable via a small task-file edit before `mine-orchestrate` runs T01/T02.
