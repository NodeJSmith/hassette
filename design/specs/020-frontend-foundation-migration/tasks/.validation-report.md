## Contradictions

### FR#7 text vs. Architecture Phase 3 (Token Mapping) — resolved in favor of Architecture, but FR#7 wording is now wrong

- **FR#7** (Functional Requirements): "shadcn/ui is initialized with New York style **and theme CSS variables mapped to the existing design token values**."
- **Architecture > Phase 3 > Token mapping**: "Deferred to spec 2. No shadcn components render in this spec (it's an explicit non-goal), so writing token aliases now would be dead code... The `shadcn init` CLI generates a default theme file; spec 2 writes the real alias mapping."
- **T04 Prompt, step 4**: "Token mapping (aliasing shadcn variables to existing design tokens) is deferred to spec 2. The generated theme file stays as-is for now."
- **T04 Verify, FR#7**: "`components.json` exists with New York style and `@/components/ui` as the component directory." — does not check token mapping.

T04 is internally consistent with the Architecture section and correctly does not attempt token mapping (consistent with the stated non-goal "Replacing hand-rolled components with shadcn equivalents (spec 2)" and the general spec-2 deferral pattern). But this means **FR#7 as literally written in the Functional Requirements list is never satisfied by any task** — the task plan silently sides with the more detailed Architecture section over the terser FR bullet, which is the right implementation call but leaves the design doc's own FR#7 text inaccurate. Fix: reword FR#7 to drop the token-mapping clause (or explicitly defer it to spec 2 in the FR text itself), so the FR and the Architecture/Verify criteria agree.

No other contradictions found between task claims and design doc text (checked: package removal timing, file deletion lists, structural-rewrite test file list, ~16/~20/~31 file-count estimates, phase sequencing, stale-closure site list, useSignalEffect migration list).
