### Task-Internal Consistency Issues (not verdict-blocking, but worth fixing)

1. **T03 dependency vs. Summary text mismatch.** T03's Summary states: "Several of these
   components import shared components converted in T02, so their TSX already works with
   the updated shared component API" — but T03's frontmatter `depends_on` is `["T01"]`
   only, not `["T01", "T02"]`. T02, T03, and T04 all declare `depends_on: ["T01"]`, which
   permits an orchestrator to run them in parallel. Since T02 (`components/shared/`) and
   T03 (`components/app-detail/`) touch disjoint files, parallel execution won't cause
   merge conflicts, and because this is a styling-only migration (DOM/props unchanged per
   Key Constraints), there's no actual functional dependency — but the Summary sentence
   is misleading as written and should either be removed or `T02` added to `depends_on`
   for clarity.

2. **T03 Target Files omission for clsx migration.** T03's Focus section instructs
   migrating `clsx` → `cn()` in `overview-tab.tsx`, `error-spotlight.tsx`, and
   `recent-activity-section.tsx` "as part of this task," but only `overview-tab.tsx`
   appears in T03's Target Files list (it has a `.module.css` to convert).
   `error-spotlight.tsx` and `recent-activity-section.tsx` have no CSS Module and are
   absent from Target Files entirely, so an executor following Target Files as its
   reading/writing scope could miss the instruction. This is not a coverage gap for
   FR#13 — T07 independently re-lists and owns all 10 `clsx` files (verified live: exactly
   10 real importers exist today, matching T07's list) with an explicit hedge ("some may
   have already been migrated in T02–T04 — check each before modifying"), so FR#13 will
   be satisfied regardless of what T03 does. Still, the duplicate/undeclared instruction
   in T03 is a planning inconsistency worth tightening (either add the two files to T03's
   Target Files, or drop the clsx mention from T03 and let T07 own it exclusively).

3. **T02 Summary/Prompt undercounts its own file count.** T02's Summary says "Convert the
   20 CSS Module files in `components/shared/`," but its Target Files list actually
   contains 26 delete entries (22 in `components/shared/` root + 4 in `log-table/`). This
   echoes an inconsistency already present in design.md itself (Architecture → Phase 2
   says "shared/ — 20 files, 1,567 lines (includes log-table subsystem)" while the
   Impact section's enumerated file list contains 26 shared/log-table entries). The
   task's actual Target Files list is correct and complete (confirmed against the live
   repo), so this is a cosmetic/prose accuracy issue inherited from the design doc, not a
   coverage gap.

### Vague Verification Criteria

Several Verify items contain a qualitative clause with no concrete command or a
subjective/unfalsifiable standard:

- **T01, FR#2**: "Focus indicator and reduced-motion rules exist in a `@layer base`
  block in global.css" — no grep command given.
- **T02, FR#13**: "All `className` composition in modified files uses `cn()`" — no
  command; only the `clsx` absence half is concrete.
- **T05, FR#3/FR#4/FR#5**: "Typography rules exist in `@layer base`..." / "Table styles
  are expressed as Tailwind utilities or `@layer components` rules..." / "Layout classes
  replaced by Tailwind utilities" — none give a command; FR#4's "or" framing makes it
  effectively unfalsifiable.
- **T05, FR#6**: The grep command itself is flawed rather than merely vague — `grep -v
  'ht-theme\|data-testid'` drops any *entire line* containing `data-testid`, so a JSX
  element with both a leftover `ht-*` class and a `data-testid` attribute on the same
  line would be silently excluded from the count, producing a false pass. Worth tightening
  to filter on the matched substring context rather than whole-line exclusion.
- **T06, FR#11**: "check_dead_tokens.py references global.css instead of tokens.css.
  check_breakpoint_drift.py is either updated or confirmed still valid" — no commands;
  "confirmed still valid" has no defined check.
- **T07, FR#12**: "The app runs in dev mode without StrictMode-related console errors" —
  requires manual dev-server + console inspection (achievable with Playwright MCP in
  this environment, but no command is specified).
- **T08, AC#11**: "Demo stack renders all pages without visual regression" — inherited
  verbatim from design.md's own AC#11 wording; no diffing procedure or baseline is
  defined, so it depends on human/visual judgment rather than a scriptable predicate.

None of these rise to "non-local" (all are attempts within the local repo/dev
environment, several with browser automation tools available), so they do not affect
the PASS verdict, but they weaken the guarantee that a Verify checkbox reflects an
objectively reproducible check.
