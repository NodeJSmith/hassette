## Coverage Gaps

### Gap #1 — Production callers of `get_apps_by_key` not explicitly migrated

The design's Replacement Targets table states the `get_apps_by_key()` → `get_running_apps()`
rename requires migrating "2 production callers + 1 test util." Verified against the current
codebase (`grep -rn get_apps_by_key src/ tests/`): the two production call sites are both in
`src/hassette/core/app_lifecycle_service.py`:

- Line 350 — inside `shutdown_all()`: `await self.shutdown_instances(self.registry.get_apps_by_key(app_key))`
- Line 502 — inside `start_app()`'s locked block (the exact code T04 is extracting into
  `_start_app_unlocked`): `instances = self.registry.get_apps_by_key(app_key)`

T04 is the only task that touches `app_lifecycle_service.py`. Its Prompt code snippets for the
`stop_app`/`start_app`/`reload_app` extraction never mention renaming either call, and its Focus
section's "gap check" items only call out test-file mock renames (`test_app_lifecycle_service.py`
lines 636/653, `test_app_lifecycle_service_operations.py` lines 52-280,
`test_app_lifecycle_service_coverage.py` lines 58/73, `conftest.py` lines 145/150). `shutdown_all()`
(line 350) is not mentioned in any task's Prompt, Focus, or Target Files reasoning at all — it
isn't even part of the stop/start/reload extraction T04 describes.

Left unaddressed, this becomes a hard `AttributeError` at runtime (and a Pyright error, since the
method is deleted in T02) the moment `shutdown_all()` or `start_app()` runs. An attentive
implementer touching the surrounding `start_app` code in T04 would likely catch the line-502
instance incidentally, but `shutdown_all()` sits outside that touched region and has no explicit
instruction anywhere in the task set.

## Contradictions

### Contradiction #1 — `unregister_app(app_key, index)` return type: design vs. task

Design (`## Edge Cases`, "`unregister_app` with index"): "`unregister_app(app_key, index)` pops
only the single entry at that index. **Returns the App if the entry was running, None
otherwise.**" — i.e. `App | None`.

T02 Prompt: "When `index` is given: pop the single entry, **return `{index: entry.app}` if entry
was running, `None` otherwise.**" — i.e. `dict[int, App] | None`.

Verified against the current implementation (`src/hassette/core/app_registry.py:49-65`): the
existing method signature is already `-> dict[int, "App[AppConfig]"] | None` for **both** the
bulk and indexed branches, and the indexed branch already wraps the result in `{index: removed}`
(line 63). T02's implementation correctly preserves this existing return-type contract; the
design doc's prose is the one that's inaccurate, describing a return shape that matches neither
the current code nor T02's own stated implementation. This is a genuine design/task mismatch —
low functional risk since T02's version is the one that actually type-checks against existing
callers, but the design doc should be corrected so the discrepancy isn't read as an unresolved
open question by whoever implements or reviews T02.

### Contradiction #2 — Frontend "status_counts" migration for `apps.tsx` summary cells is not grounded in the actual code

Design (`## Architecture` → Frontend): "Frontend reads from the nested `status_counts` object
(e.g., `data.status_counts.running`)." T05 Prompt: "Update the summary `cells` array to read from
the nested `status_counts` object instead of top-level fields (e.g., `data.status_counts.running`
instead of `data.running`)."

Verified against the live frontend code:

- `frontend/src/pages/apps.tsx`'s `buildAppsCells()` computes its `statusCounts` **locally**, by
  iterating each row's live status via `appLiveStatus(appStatuses, a)` — not from any API
  response field (`apps.tsx:63-78`).
- `apps.tsx` doesn't even consume `AppManifestListResponse`/`AppFullSnapshot` — its data source is
  `getDashboardAppGrid` (a different endpoint), not `/api/apps/manifests`.
- `useManifests()` (`frontend/src/hooks/use-manifests.ts`), the hook that *does* wrap the
  manifests-list endpoint, unwraps the response down to `AppManifest[]` via
  `select: (data) => data.manifests`, discarding the count fields entirely before any component
  sees them.
- A repo-wide grep of `frontend/src` for `.running`/`.failed`/`.stopped`/`.disabled`/`.blocked`
  access finds no consumer of `AppManifestListResponse`'s count fields outside test/factory files
  (`frontend/src/test/factories.ts`, `frontend/src/test/handlers.ts`,
  `frontend/src/hooks/use-manifests.test.ts` — which T05 does correctly target).

There is nothing in `apps.tsx` to "migrate to nested `status_counts`" — the change the design and
T05 describe doesn't correspond to any existing code path. Notably, T05's own Focus section
already flags uncertainty here ("the `cells` code currently reads `statusCounts.running`... but
`statusCounts` is locally computed from the manifest list, not from the API response's count
fields. Trace the data flow carefully...") but stops short of correcting the Prompt's definitive
(and incorrect) instruction. The Prompt and the Focus note disagree within the same task file,
which either sends the implementer chasing a nonexistent data-flow change or, if they trust the
Focus hedge instead, leaves the Prompt's explicit instruction silently unactioned with no
Verify-level way to tell which happened. The only real, necessary frontend change in this area
(confirmed correct) is adding `degraded: 0` to the local `statusCounts` initializer at
`apps.tsx:64`, which T05 already instructs separately and correctly.
