## Coverage Gaps (blocking)

### Gap 1 — AC#7 only partially verified

Design doc AC#7 (line 105) is a single `ls` command over **9 files**: `button.tsx`, `badge.tsx`, `chip.tsx`, `card.tsx`, `tooltip.tsx`, `confirm-dialog.tsx`, `info-popover.tsx`, `column-filter-popover/index.tsx`, `command-palette.tsx`.

T02's frontmatter declares `implements: [..., "AC#7", ...]`, but T02's own Verify checklist only runs:

```
ls frontend/src/components/shared/button.tsx frontend/src/components/shared/badge.tsx frontend/src/components/shared/chip.tsx frontend/src/components/shared/card.tsx frontend/src/components/shared/tooltip.tsx 2>/dev/null
```

— 5 of the 9 files. The other 4 (`confirm-dialog.tsx`, `info-popover.tsx`, `column-filter-popover/index.tsx`, `command-palette.tsx`) are deleted in T03, but T03's frontmatter does **not** list AC#7 in `implements`, and T03's Verify checklist never checks for their absence. No task ever runs the complete AC#7 grep. T02 claiming AC#7 "done" is also premature — those 4 files still exist when T02 finishes, since T03 hasn't run yet.

**Fix:** Either (a) split AC#7 across T02 (5-file check) and T03 (4-file check, added to T03's implements/Verify), or (b) move the full 9-file AC#7 check to T06 (the final integration task) once all deletions are complete.

### Gap 3 — No final AC#1/AC#3 checkpoint after parallel branches merge

Dependency graph:

```
T01 → T02 → T03 → T04 ─┐
        └──→ T05 ───────┼──→ T06
```

T04 (tables) and T05 (sidebar) both depend only on earlier ancestors (T04 on T03→T02→T01; T05 on T02→T01) and are mutually independent — they can execute in either order or in parallel. Each checks AC#1 (`npm run build`)/AC#3 (`npm run typecheck`) against its *own* branch state, but neither branch's check reflects the other branch's changes merged in.

T06 is the only task with `depends_on: ["T04", "T05"]` — the actual merge point of the whole plan — but T06's `implements` is `["FR#17", "AC#2", "AC#9", "AC#10"]`. It does **not** re-run `npm run build` or `npm run typecheck` as an explicit Verify step. AC#9 (e2e) and AC#10 (demo) would likely fail if the build were broken, but they are not the literal build/typecheck commands AC#1/AC#3 specify, and a typecheck failure in an unused code path wouldn't necessarily surface in e2e or a visual demo pass.

**Fix:** add AC#1 and AC#3 to T06's `implements` and Verify checklist as the final confirmation that the fully-merged tree builds and typechecks clean.

## Contradictions (design-doc-level, not task-file faults)

These are pre-existing inconsistencies in `design.md` itself. The task files resolved them sensibly (by following the more specific/authoritative statement), so they do not by themselves indicate a defect in the task plan — but they should be cleaned up in the design doc, and are noted here since the FAIL verdict criteria technically include "contradictions."

1. **time-preset-selector.tsx: delete vs. restyle.** Line 434 (Impact > Deleted Files) says:
   > `delete frontend/src/components/layout/time-preset-selector.tsx + .module.css + .test.tsx`

   This directly contradicts FR#10 ("restyled with Tailwind utilities... keeping the existing markup"), the Replacement Targets table (line 259, "Restyle in place; shadcn replacement deferred"), and AC#7's own clarifying note (line 105, "`time-preset-selector.tsx` and `sidebar.tsx` are restyled in place, not deleted"). T03 correctly treats it as `modify`, not `delete`, consistent with the majority of the doc and the explicit AC#7 note. **Recommend deleting the stray bullet at line 434.**

2. **"Do not modify CSS Module files" vs. sidebar/time-preset-selector restyle.** Key Constraints (line 115) states a blanket rule: "Do not modify CSS Module files. They must continue working for the transition period. PR 2 handles their conversion to Tailwind utilities." But FR#10, FR#12, and the Impact list (line 441, `sidebar.module.css — restyle with Tailwind`) explicitly call for modifying `sidebar.module.css` and `time-preset-selector.module.css` as part of this PR. T03 and T05 correctly modify those two specific files while leaving the other ~61 CSS Modules untouched — a sensible reading, but the blanket constraint as literally written doesn't carve out this exception. **Recommend adding an explicit exception clause** ("...except `sidebar.module.css` and `time-preset-selector.module.css`, which are restyled in place per FR#10/FR#12").
