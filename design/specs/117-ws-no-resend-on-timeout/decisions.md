# Decisions — #1798: stop re-sending non-idempotent WS commands on response timeout

**Issue:** #1798 · **Prior work:** PR #2252 (shipped in 0.55.0: `retry_on_timeout` on `send_and_wait` / `Api.ws_send_and_wait`, `wait_for_ack` on `call_service`) · **Source:** audit F2, `design/audits/2026-09-02-backend-core-correctness-audit.md`

## Summary

`WebsocketService.send_and_wait` retries any `FailedMessageError` with `code is None`, which includes a
*response* timeout after the payload already reached Home Assistant. The retry re-sends under a fresh
message id, so HA applies the command again. PR #2252 added the `retry_on_timeout` opt-out and used it
only for `call_service(wait_for_ack=True)`. This work closes the remaining open criteria: `fire_event`,
`call_service(return_response=True)` without `wait_for_ack`, and helper `create`/`update`/`delete`
(via `_ws_helper_call`) all stop re-sending on response timeout, and a response timeout raises a
distinguishable `FailedMessageError` subtype meaning "sent, outcome unknown". Reads (`get_states`,
`get_config`, `get_services`, `get_panels`, helper `list`) keep retrying. **Out of scope:** REST-path
retries (`rest_request` re-sending POST/DELETE), changes to `subscribe_events`' own retry loop,
the retry count/backoff policy, and any HA-side deduplication (HA's WS API has no idempotency key).

Answers given one at a time. Each row's number refers to the table below. The "Needs your call" table keeps the options and rationale as they were originally presented. Where the two disagree, this section wins.

| 2 | **A.** No `call_service` path re-sends. `_call_service` passes `retry_on_timeout=False` on both waiting paths (`return_response` and `wait_for_ack`). `call_service` gets no new kwarg, so its signature, the sync facade, `ApiProtocol`, the recording doubles, and the generated entity wrappers are unchanged. `wait_for_ack` goes back to meaning only "wait for the envelope". The generated read helpers (`todo.get_items`, `weather.get_forecasts`, `media_player.browse_media`/`search_media`) lose their retry on a rare timeout. A caller who wants a retry catches `ResponseTimeoutError` and retries; that's simple to write against the primitive, so it doesn't earn a convenience kwarg (CLAUDE.md, "Convenience APIs must earn their place"). |
| 3 | **A, under a shared marker parent.** `OutcomeUnknownError(HassetteError)` is a marker class: a docstring and no body. It means "sent, but no response arrived, so it may or may not have applied". There are two concrete subclasses, and each takes its constructor and attributes from its second base: `ResponseTimeoutError(OutcomeUnknownError, FailedMessageError)` and `ResponseLostError(OutcomeUnknownError, RetryableConnectionClosedError)` (see #8). Callers catch `OutcomeUnknownError` once for both. Because the marker has no `__init__`, the two parents' constructors never meet. `ResponseLostError` is not a `FailedMessageError`, so the retry predicate (#7) and `_ws_helper_call`'s `except FailedMessageError` never match it. Neither class subclasses `TimeoutError`. |
| 4 | `OutcomeUnknownError` (parent), `ResponseTimeoutError` (timeout), `ResponseLostError` (disconnect while waiting). |
| 5 | **A.** Raised for every response timeout: single-attempt writes and the last attempt of a retried read. |
| 6 | **A.** For every `OutcomeUnknownError`, the message names the command `type`, msg id, and the cause (timeout seconds, or disconnect), with no payload values. `ResponseTimeoutError` carries the full payload on `original_data` (a `FailedMessageError` attribute). `ResponseLostError` carries `close_code`, like any `RetryableConnectionClosedError`, and no payload. |
| 7 | **A.** The retry predicate is unchanged. It still matches `ResponseTimeoutError` (a `FailedMessageError` with `code is None`), so reads retry on timeout. It doesn't match `ResponseLostError` (#3). |
| 8 | **B.** When the connection drops while `send_and_wait` is waiting for a response, `cleanup()` or `partial_cleanup()` (reconnect) fails the pending future with `RetryableConnectionClosedError`. `send_and_wait` re-raises that as `ResponseLostError` for every send, reads included, to match #5. It isn't a `FailedMessageError`, so the unchanged predicate doesn't retry it. A disconnect isn't retried today, and it still won't be. |
| 9 | **A.** Out of scope. File a follow-up issue for REST POST/DELETE retries. |
| 10 | Keep `retry_on_timeout` on `ws_send_and_wait`. It remains the only public method with the kwarg. |
| 11 | `fix:`, non-breaking. No signature changes, and `ws_send_and_wait` keeps its default. Two shipped behaviors do change. `call_service(return_response=True)` without `wait_for_ack` stops retrying on timeout, and so does `fire_event`. A disconnect while waiting now raises `ResponseLostError`, which existing `except RetryableConnectionClosedError` handlers still catch. The changelog line names both behavior changes, plus helper create/update/delete, and the new `OutcomeUnknownError` family. It tells callers who relied on the retry to catch `OutcomeUnknownError` and decide for themselves whether to retry. |
| 12 | **Logging for unknown outcomes.** (a) `send_and_wait` logs a WARNING, with the redacted message from #6, whenever it raises an `OutcomeUnknownError` to its caller. That covers a non-retried send, a retried read's final timeout, and a disconnect. The log sits at the single point where the error leaves `send_and_wait`, so no branch on retried versus non-retried is needed. One WARNING per event is deliberate, even in a storm where HA degrades and many writes time out together. `LoggingService`'s bounded queues and drop counters, plus the database's age-based retention, cap the resource cost, so there's no aggregation. That record survives even if an app swallows the exception. (b) **Late replies to timed-out writes.** A late reply is the only thing that settles #12a's "may have applied", and only for writes; a late reply to a read settles nothing. So `WebsocketService` records the msg id → command `type` of each **non-retried** send that raises `ResponseTimeoutError`, registered where #12a's WARNING fires, which gives one id per write. Retried reads are never recorded. The record is an `OrderedDict` capped by a module constant (100), with the oldest entry evicted first. It is cleared in both `cleanup()` and `partial_cleanup()`, next to `_response_futures.clear()`, because msg ids belong to one connection. When a late result envelope matches an entry, `respond_if_necessary` logs it and drops the entry: INFO for `success` (the write applied after the timeout) and WARNING for a failure (the write did not apply). Both lines name the `type` and id. Replies to fire-and-forget sends and reads match no entry and stay silent. Tests: a late success and a late failure each log at their level, a reconnect clears the record, and the cap evicts the oldest entry. |
| 13 | **Recovery guidance.** Docs tell callers how to resolve an `OutcomeUnknownError`. After a helper `create`/`update`/`delete`, call `helpers.list(domain)` to check whether it landed. `managing-helpers.md` shows this pattern as code, and the `OutcomeUnknownError` docstring points to it. `fire_event` and `call_service` can't confirm that their side effect took effect (a requested service response reports only what HA chose to return), so checking the side effect is the caller's job; for example, read the target entity's state. `methods.md` says this next to the `!!! warning` from Assumed. |
| 14 | **Testing example.** `docs/pages/testing/harness.md` gains an example that patches a recorder method with `AsyncMock(side_effect=ResponseTimeoutError(...))` and asserts how the app handles it. The example lives in a snippet file under `docs/pages/testing/snippets/`, included with `--8<--` like the rest of the page. |

## Assumed

- `fire_event` sends exactly once on response timeout. Evidence: acceptance criterion 1 and the open checkbox in the #2252 follow-up comment.
- Helper `create`/`update`/`delete` send exactly once, and `list` keeps retrying. Evidence: the #1798 "Scope addition" comment. (`update` is effectively idempotent, but a retried `delete` that already applied raises a false `not_found`, so all three are treated the same.) Under #1-B, `_ws_helper_call` needs a way for the three writes to pass `retry_on_timeout=False` while `list` keeps the retrying default.
- The `subscribe_events` retry loop is untouched. Evidence: acceptance criterion 3.
- `_ws_helper_call` must not erase `ResponseTimeoutError`. Today its `except FailedMessageError` rebuilds every error as a plain `FailedMessageError`. It passes `OutcomeUnknownError` subtypes through unwrapped instead, since #6 already keeps their messages free of payload values, so the redaction the rewrap exists for isn't needed. `ResponseLostError` isn't a `FailedMessageError` and passes through untouched, as disconnects do today. Test: a helper-CRUD timeout raises `ResponseTimeoutError`, and a helper-CRUD disconnect is still `isinstance(..., RetryableConnectionClosedError)`. Evidence: `src/hassette/api/api.py:250-274`.
- The new exceptions live in `src/hassette/exceptions.py` next to `FailedMessageError` and keep the `code is None` meaning "locally synthesized". Evidence: the `FailedMessageError` docstring and `docs/pages/troubleshooting.md:224`. Per #6, `original_data` on a `ResponseTimeoutError` is the outgoing request payload, not an HA response envelope. The `ResponseTimeoutError` docstring and the `original_data` description on `FailedMessageError` both say so.
- `wait_for_ack` keeps its name and default. Only its docstring and docs change: the "declares non-idempotent" sentence goes away (#2). Evidence: shipped in 0.55.0 (`CHANGELOG.md:18`).
- No public signature changes (#1, #2), so `ApiProtocol`, `RecordingApi`, `testing/_sync_facade.py`, and the generated entity wrappers need no edits. `src/hassette/api/sync.py` copies `Api` docstrings, so regenerate it (`codegen/src/hassette_codegen/sync_facade/ --target api`) after the `api.py` docstring edits. ## Made during implementation

- Commits went to `1798-decision-ledger-opus` (this worktree's branch), not `1798-decision-ledger` as Assumed names it.
- The exception family landed as its own commit before the RED tests, so RED fails on behavior rather than on an `ImportError`.
- `_ws_helper_call` gained a keyword-only `retry_on_timeout: bool = True` and always forwards it explicitly; `list` passes the default, so the existing exact-call assertions in `test_api_helpers.py` now include `retry_on_timeout=True`.
- `_ws_helper_call` passes `OutcomeUnknownError` through with an explicit `except OutcomeUnknownError: raise` placed before the `FailedMessageError` rewrap, with a comment saying why the order matters.
- Message wording: `'<type>' (id N): no response within Ns; the command may or may not have applied` and `'<type>' (id N): connection lost while waiting for a response; the command may or may not have applied`.
- A payload with no `type` renders as `'None'` in messages and in the late-reply record (`str(data.get("type"))`).
- `ResponseTimeoutError.original_data` is a copy of the outgoing payload, including the `id` field `send_and_wait` assigned.
- `ResponseTimeoutError` keeps the existing `from None`; `ResponseLostError` is chained `from` the `RetryableConnectionClosedError` it replaces.
- The disconnect conversion catches any `RetryableConnectionClosedError` out of `send_and_await_response`; in practice only the cleanup-failed future raises it there.
- Each attempt uses a local `attempt_id`, mirrored to an outer `last_attempt_id: int | None` that the post-retry handler reads for the late-reply record.
- The #12a WARNING message is exactly the exception's `str`.
- Names: `TIMED_OUT_WRITE_RECORD_CAP` (module constant in `websocket_service.py`), `_timed_out_writes`, `_record_timed_out_write`, `_settle_timed_out_write`.
- The late-reply lookup runs only when no response future exists for the id; a reply whose future is still pending or already done takes the existing paths.
- The late-failure WARNING includes HA's error `code` but not its error `message`, since the message can echo payload values.
- Late-reply log wording: INFO `Late reply to timed-out '<type>' (id N): it succeeded, so the command applied after the timeout`; WARNING `... Home Assistant reported failure (code '<code>'); check state before re-sending`.
- A send with a caller-provided `id` is recorded the same way as one with a generated id.
- Docstrings beyond the listed ones: `Raises` sections on `WebsocketService.send_and_wait` and `call_service`; `ws_send_and_wait`'s `retry_on_timeout` doc names `ResponseTimeoutError`; a one-line comment in `_fire_event`; `FailedMessageError`'s class docstring gained an `original_data` paragraph (it had no attribute docstring).
- The `OutcomeUnknownError` docstring points to the "Managing helpers" docs page by name, not by URL.
- The new exceptions aren't exported from `hassette/__init__.py`, matching `FailedMessageError`.
- The helper-CRUD comment about counter shortcuts in `helpers.py` was left as is; "sends each call exactly once" is still true.
