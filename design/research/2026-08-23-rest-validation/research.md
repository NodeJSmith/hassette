# Research Brief: Runtime REST API Response Validation

**Initiated by**: Issue #1677 -- add runtime validation for REST API responses mirroring the existing WebSocket Ajv validation.

## Context

### What prompted this

`apiFetch<T>()` in `frontend/src/api/client.ts` (line 44) does `response.json() as Promise<T>` -- a pure compile-time assertion with zero runtime validation. Every REST endpoint function in `endpoints.ts` threads a generated type through this cast, giving callers a false guarantee: the TypeScript compiler believes the data matches `components["schemas"]["X"]`, but nothing at runtime confirms it.

The WebSocket path, by contrast, validates every inbound frame through `validateWsMessage()` in `ws-validator.ts` -- an Ajv-compiled validator against `ws-schema.json` that throws `WsValidationError` on any shape mismatch. This asymmetry is documented explicitly in the codebase: the `isKnownMapKey()` function in `status.ts` (line 22) and its four consumers all carry docstrings explaining they exist "because REST responses are never runtime-validated against the schema." The design spec for this pattern (`design/specs/102-status-exhaustiveness-enforcement/design.md`, archived) states the same rationale.

Real bugs have occurred from this gap -- PR #1605 added `ManifestStatus.DEGRADED` and five frontend consumers silently missed it, producing undefined-key lookups at runtime because nothing validated the enum value before it reached the status maps.

### Current state

**WS validation (the reference pattern):**
- `ws-validator.ts` creates a single Ajv instance (`new Ajv({ discriminator: true })`) and compiles `ws-schema.json` at module load time -- one singleton, one compile, amortized across all messages.
- `validateWsMessage(data: unknown): WsServerMessage` throws `WsValidationError` (carries `ErrorObject[]`) on failure, returns the narrowed typed value on success.
- The sole call site (`use-websocket.ts`, `socket.onmessage`) catches `WsValidationError`, logs `console.warn`, and drops the malformed frame -- the socket stays alive, other messages keep flowing.
- `ws-schema.json` (698 lines, 15.7 kB, ~1.9 kB gzipped) is a single discriminated union (`oneOf` with 6 branches keyed by `type`), imported as a static JSON module and inlined into the bundle by Vite.

**REST client (no validation):**
- `apiFetch<T>()` handles HTTP errors (non-ok responses throw `ApiError`) but trusts the body shape unconditionally.
- All 20 endpoint functions in `endpoints.ts` call `apiFetch<SomeType>(path)`, and 21 consumer files across pages, hooks, and shared components receive the unvalidated data through TanStack Query hooks.
- The only runtime safety net is the app-wide `ErrorBoundary` in `app.tsx` -- if a malformed response causes a render-time `TypeError` (e.g., destructuring a missing field), the entire routed page blanks with a generic "Something went wrong" card.

**Schema infrastructure:**
- `openapi.json` (OpenAPI 3.1.0, 62 kB raw, ~10.1 kB gzipped) is generated by FastAPI's `app.openapi()` backed by Pydantic v2's `model_json_schema()`. It contains 29 paths and 36 named schemas in `components.schemas`.
- `ws-schema.json` is generated by Pydantic's `TypeAdapter(WsServerMessage).json_schema()`.
- Both are JSON Schema 2020-12 dialect (OpenAPI 3.1 mandates this). Both generated by the same Pydantic v2 (2.12.3) core. The schemas use identical patterns: `anyOf: [{type: T}, {type: null}]` for nullable fields, `enum` for string enums, `$ref` for composition.
- Key structural difference: `ws-schema.json` refs use `#/$defs/Name`, OpenAPI uses `#/components/schemas/Name`. Same JSON Pointer mechanics, different root.
- OpenAPI response schemas are overwhelmingly `$ref` to named schemas. Nine list-returning endpoints use inline `{type: array, items: {$ref: ...}}` wrappers. One endpoint returns `Execution | null` via inline `anyOf`.
- No `additionalProperties: false` appears on any response schema -- Ajv will allow extra properties by default, meaning a backend adding new fields won't break validation.
- Six `additionalProperties` usages exist, all on intentionally open-ended dict fields (`status_counts: dict[str, int]`, `config_schema: dict[str, Any]`, `config_values: dict[str, Any]`).

### Key constraints

**Bundle budget is the dominant constraint.** The entry chunk is 234.28 kB gzipped against a 240 kB budget (`.size-limit.json`) -- 5.7 kB of headroom. Ajv (^8.20.0) is already a production dependency shipped in the entry chunk via `ws-validator.ts`. REST types currently cost zero bytes at runtime (all `import type` statements, erased at compile time). Any runtime validation adds net-new cost.

Specific size measurements:
- Full `openapi.json`: 62 kB raw, 10.1 kB gzipped -- importing it wholesale as the WS path imports `ws-schema.json` would blow the budget by ~4.4 kB.
- `components.schemas` only (stripping paths/parameters/metadata): 30.8 kB raw, 5.8 kB gzipped -- exactly at the budget limit, no margin.
- Ajv standalone precompilation (`ajv/dist/standalone`) is available in the installed package but unused -- it produces pure validation functions that need only Ajv's tiny runtime helpers, not the full compiler.

## Feasibility Analysis

### What would need to change

| Area | Files affected | Effort | Risk |
|------|---------------|--------|------|
| Build pipeline: schema extraction + precompilation | 1-2 new scripts | Med | New build step to maintain |
| REST client (`client.ts`) | 1 file | Low | Signature change, but mechanical |
| Endpoint functions (`endpoints.ts`) | 1 file, 20 functions | Low | Mechanical wiring |
| Defensive guards (`status.ts`, `status-priority.ts`) | 2 files | Low | Removal, not addition |
| Tests (`client.test.ts`, new validator tests) | 2-3 files | Low | Straightforward |
| Size budget (`.size-limit.json`) | 0-1 file | Low | May need adjustment |

**Direct changes:**
- A new build script (analogous to `scripts/generate-ws-types.cjs`) that extracts response schemas from `openapi.json`, compiles them via Ajv standalone, and outputs a generated module mapping schema names to precompiled validate functions.
- `apiFetch<T>()` gains an optional `validate` parameter (or a registry lookup), calls it before returning, and handles failures per the chosen semantics.
- Each endpoint function in `endpoints.ts` passes its corresponding validator.

**Cascade changes:**
- `isKnownMapKey()` and its four consumer functions in `status.ts` can be simplified once validation is in place -- the runtime guard becomes redundant when the schema guarantees enum membership. The compile-time `satisfies Record<Union, X>` exhaustiveness checks remain valuable on their own.
- `?? UNKNOWN_PRIORITY` fallback in `status-priority.ts` becomes dead code.
- Defensive `typeof` checks in `config-schema-view.tsx` remain necessary -- `config_schema` is `dict[str, Any]` by design, not schema-validatable.

**Test changes:**
- New test file for the REST validator module (mirroring `ws-validator.test.ts`).
- Updated `client.test.ts` to verify validation wiring and failure handling.

### What already supports this

1. **Ajv is already bundled** -- no new library to add. The full Ajv compiler ships today for WS validation.
2. **Schema generation pipeline exists** -- `scripts/export_schemas.py` + `scripts/schema_helpers.py` already generate `openapi.json` from the live FastAPI app. The `tools/check_schemas_fresh.py` pre-push hook ensures schema freshness.
3. **Same JSON Schema dialect** -- both WS and REST schemas are Pydantic v2's JSON Schema 2020-12 output. The same Ajv configuration works for both.
4. **Single chokepoint** -- all REST calls funnel through `apiFetch()` in `client.ts`. Validation can be wired once, not scattered.
5. **Endpoint-to-schema mapping is trivial** -- `openapi.json`'s `paths` section maps each endpoint to its response `$ref`. The 20 endpoint functions in `endpoints.ts` already name their types explicitly.
6. **No `additionalProperties: false`** -- the schemas are forward-compatible by default. A backend adding new optional fields won't break existing validators.
7. **Established precedent** -- the design spec for `isKnownMapKey` (spec 102) explicitly calls out this validation gap as the root cause and names REST validation as the proper fix.

### What works against this

1. **5.7 kB budget headroom** -- the tightest constraint. Importing raw schemas (even just `components.schemas` at 5.8 kB gzipped) exceeds the budget. This effectively mandates either standalone precompilation or raising the budget.
2. **No existing build-time compilation step** -- the WS path compiles at runtime (`ajv.compile()` in browser code). REST validation needs a new pattern (build-time precompilation) or the budget must be raised.
3. **REST has per-endpoint schemas, not one union** -- the WS path compiles one discriminated-union schema. REST has 36 named schemas referenced by 29 endpoints. The validation module is structurally different -- a registry of validators, not a single function.
4. **Enum forward-compatibility tension** -- the exact scenario `isKnownMapKey` defends against (backend sends a new enum value the frontend doesn't know) would cause validation failure under strict enum checking. This is both the problem and a design decision: should unknown enum values be rejected or tolerated?
5. **`Execution | null` endpoint** -- `/api/telemetry/execution/{id}` returns an inline `anyOf: [Execution, null]` rather than a named schema. Needs special handling in the validator registry.

## Options Evaluated

### Option A: Ajv standalone precompilation (primary -- user's leaning, refined)

**How it works:** A build-time script extracts the `components.schemas` section from `openapi.json`, resolves all `$ref` pointers within it, and runs `ajv.compile()` + Ajv's `standaloneCode()` for each response schema to produce a generated TypeScript module (`frontend/src/api/rest-validators.generated.ts`) exporting one validate function per schema. These functions are pure JavaScript -- they check the data shape using `if/else` chains, not schema interpretation, and depend only on Ajv's tiny runtime helpers (`ajv/dist/runtime/...`), not the full schema compiler.

At runtime, `apiFetch()` accepts an optional `ValidateFunction` parameter. Each endpoint function in `endpoints.ts` passes its precompiled validator. On validation failure, `apiFetch()` handles it according to the chosen failure semantics (see Open Questions). The generated validator file is checked into the repo alongside `generated-types.ts` and refreshed by the same `export_schemas.py` pipeline.

The existing WS path could optionally migrate to precompiled validators too, which would let the full Ajv compiler (`ajv` default import) be replaced with `ajv/dist/runtime` only -- a substantial bundle size reduction. This is a follow-up optimization, not a prerequisite.

**Pros:**
- Mirrors the established WS validation pattern (Ajv, throw-on-failure, schema-from-Pydantic).
- No new runtime dependency -- Ajv is already bundled.
- Precompiled validators are small (each is a few hundred bytes of `if/else` logic) and fast (no schema interpretation at runtime).
- Net bundle impact could be near-zero or even negative: precompiled REST validators add a few kB, but migrating WS to precompiled too would remove the full Ajv compiler (~20-30 kB gzipped estimate) and replace it with the runtime-only package (~3-5 kB).
- Validation happens at build time -- schema compilation errors surface during `npm run build`, not at page load.
- Forward-compatible: no `additionalProperties: false` in the schemas, so extra fields from a newer backend pass through silently.
- The `openapi.json` file itself is never shipped to the browser -- only the tiny precompiled functions are.

**Cons:**
- Adds a new build step to the pipeline -- another generated file to keep in sync.
- Ajv's standalone mode has constraints: only `code` and `macro` user-defined keywords are supported, and some schema features may not precompile cleanly (though Pydantic's output is well-behaved).
- The `$ref` resolution from `#/components/schemas/` needs handling during precompilation (Ajv can do this natively when the full document is registered, but the standalone codegen needs the refs resolved first).
- Each endpoint function in `endpoints.ts` needs a one-line addition to pass its validator -- 20 mechanical changes.

**Effort estimate:** Medium. The precompilation script is the main new work (~100-200 lines). The wiring into `apiFetch` and `endpoints.ts` is mechanical. The `isKnownMapKey` cleanup is a straightforward deletion.

**Dependencies:** No new packages. Ajv 8.20.0's `ajv/dist/standalone` is already installed.

### Option B: Runtime Ajv with extracted schemas (comparison alternative)

**How it works:** Instead of precompiling, extract just the `components.schemas` object from `openapi.json` into a separate JSON file at build time (stripping paths, parameters, and metadata). Import this extracted file as a JSON module (same pattern as `ws-schema.json`). At module load, register the schemas with Ajv via `ajv.addSchema()` and lazily compile validators on first use per endpoint via `ajv.getSchema("#/components/schemas/TypeName")`.

**Pros:**
- Simpler build step -- extraction is a JSON filter, not a compilation.
- Mirrors the WS path more directly (same runtime `ajv.compile()` pattern).
- Easier to debug -- schema errors surface as runtime Ajv errors with readable paths.

**Cons:**
- `components.schemas` alone is 5.8 kB gzipped -- exactly at the 5.7 kB budget limit, with no room for the validator registry code, the endpoint-to-schema mapping, or any future schema growth.
- Full Ajv compiler stays in the bundle (needed for runtime compilation) -- no path to the bundle reduction that Option A enables.
- First-use compilation adds latency on the first API call per endpoint type (Ajv's compile is fast but not free).
- Schema is shipped to the browser as raw JSON -- inspectable in DevTools, which is not a security concern for this project but is less clean.

**Effort estimate:** Small. The extraction script is trivial. Wiring is the same as Option A (one-line change per endpoint function). But the budget constraint makes this infeasible without raising the limit.

**Dependencies:** None new.

## Failure Semantics Analysis

This was identified as a key research question. The WS path's behavior provides the starting point, but REST has fundamentally different failure characteristics.

**WS path behavior:** `validateWsMessage()` throws on failure. The caller (`use-websocket.ts`) catches, `console.warn`s, and drops the bad frame. This works because WebSocket is a stream -- one dropped message doesn't break the application; the next message will carry updated state.

**REST is different:** Each response is individually awaited by a component (via TanStack Query). "Drop and continue" doesn't apply -- the component needs data to render. The options:

| Strategy | Behavior | When schema drifts | Trade-off |
|----------|----------|-------------------|-----------|
| **Always throw** | Bad data never reaches components | Component hits ErrorBoundary, page blanks | Clean contract, but harsh UX for minor drift |
| **Dev-only throw** | Throw in development, warn+pass in production | Dev catches it early, prod degrades gracefully | Different behavior per environment complicates testing |
| **Warn and pass through** | Log mismatch, return data anyway | Console noise, but UI keeps working | Defeats strict validation; data may still cause runtime errors downstream |
| **Throw on structural, warn on enum** | Reject missing/wrong-typed fields; tolerate unknown enum values | Structural breaks caught, new enum values pass through | Directly addresses the `isKnownMapKey` scenario |

The fourth option ("throw on structural, warn on enum") is the most interesting because it directly addresses the tension between strict validation and forward compatibility. The `isKnownMapKey` guards exist because a new backend enum value would be an unknown string at the frontend -- strict enum validation would reject it, which is arguably *worse* than the current graceful fallback. But structural mismatches (missing fields, wrong types) are genuine bugs that should fail fast.

Ajv supports this via error filtering: validate with full schemas (including enums), then inspect `validate.errors` to distinguish structural failures (`type`, `required`, `properties` keywords) from enum failures (`enum` keyword). Structural errors throw; enum errors warn.

**Note:** This is a product decision, not a technical limitation. All four options are implementable with Option A or B. The recommendation section suggests a default but flags this as needing user input.

## Concerns

### Technical risks

- **`$ref` resolution during standalone precompilation.** OpenAPI schemas use `#/components/schemas/Name` as the ref root. Ajv's standalone codegen needs the full document registered (or refs pre-resolved) to emit valid code. This is a well-documented Ajv pattern but needs careful implementation -- a broken ref produces a build-time error (good) but debugging Ajv's ref resolution errors can be cryptic.
- **Inline response schemas.** One endpoint (`/api/telemetry/execution/{id}`) returns `anyOf: [Execution, null]` rather than a named schema. The precompilation script needs to handle this case -- either by generating a one-off validator or by treating `T | null` as "validate against T, also accept null."
- **Ajv 2020-12 dialect.** The current `ws-validator.ts` uses `new Ajv()` (which targets JSON Schema draft-07 by default), not `new Ajv2020()`. The schemas are draft 2020-12 but simple enough that draft-07 validation works. Standalone precompilation may require explicit `Ajv2020` if the codegen is stricter about dialect conformance. Worth verifying during implementation.

### Complexity risks

- **Another generated file.** The project already manages `openapi.json`, `ws-schema.json`, `generated-types.ts`, and `ws-types.ts` through a pipeline. Adding `rest-validators.generated.ts` is incremental, not novel -- but it is one more artifact that `check_schemas_fresh.py` must track.
- **Validator threading.** Each of the 20 endpoint functions gains a validator parameter. This is mechanical but touches a high-traffic file. If an endpoint is added and the developer forgets to wire its validator, the response silently skips validation (same as today). A lint rule or helper type could enforce completeness.

### Maintenance risks

- **Schema growth.** As new endpoints and response models are added, the precompiled validator file grows. At 36 schemas today, this is modest. If the schema count doubles, the generated file size needs monitoring -- but precompiled validators are much more compact than raw schemas.
- **Ajv standalone API stability.** The standalone codegen API (`standaloneCode()`) has been stable since Ajv 8.x but is less widely used than the core validator API. Breaking changes in a future Ajv major version would require updating the build script.

## Open Questions

- [ ] **Failure semantics: which strategy?** The "throw on structural, warn on enum" approach directly addresses the `isKnownMapKey` scenario while keeping strict validation for shape mismatches. But this is a product call -- should unknown enum values crash the page (always-throw), or should they degrade gracefully (warn on enum)? The current `isKnownMapKey` pattern chose graceful degradation; validation could preserve or override that choice.
- [ ] **Should WS validation also migrate to precompiled?** Migrating WS to standalone precompilation would remove the full Ajv compiler from the bundle, potentially saving 15-25 kB gzipped. This is a follow-up optimization but worth deciding upfront since it affects whether `new Ajv()` stays in the codebase at all.
- [ ] **Should the size-limit budget be raised?** If Option B is preferred (simpler, no precompilation), the 240 kB limit would need to increase by ~6-8 kB. The current 240 kB was set before REST validation was planned. Is the budget a hard constraint or a soft guideline?
- [ ] **Where should the precompilation script live?** Candidates: `scripts/compile-rest-validators.cjs` (alongside `generate-ws-types.cjs`), integrated into `export_schemas.py` (Python driving Node), or a new `tools/frontend/` script (matching the existing CSS hygiene scripts there).

## Recommendation

Option A (Ajv standalone precompilation) is the stronger path. It solves the immediate problem (REST validation parity with WS) while opening a follow-up that could reduce the overall bundle size by migrating WS validation to precompiled too. The bundle constraint makes Option B infeasible without raising the size limit, and raising the limit feels like the wrong trade when a precompilation approach avoids the cost entirely.

For failure semantics, "throw on structural mismatches, warn on unknown enum values" is the pragmatic default. It gives strict validation where it matters most (missing fields, wrong types) while preserving the graceful degradation that `isKnownMapKey` already provides for the enum-drift case. The `isKnownMapKey` guards can then be removed -- the validator's enum-warning path replaces them -- and the compile-time `satisfies Record<Union, X>` checks remain as the exhaustiveness enforcement.

Confidence: the feasibility analysis is **Direct** (grounded in specific file reads, measured bundle sizes, and confirmed schema structures). The bundle-size impact of precompilation is **Inferred** -- Ajv's standalone docs describe the mechanism, but the actual gzipped size of 36 precompiled validators hasn't been measured. A prototype that precompiles a few schemas and measures the output size would resolve this before committing to the full implementation.

### Suggested next steps

1. **Prototype the precompilation script** -- precompile 3-4 representative schemas (one simple object, one with nested refs, one array-of-ref, the `Execution | null` inline case) and measure the generated code size gzipped. This resolves the remaining size uncertainty.
2. **Write a design doc via `/mine-define`** -- the failure semantics question and the WS migration follow-up need explicit decisions before implementation.
3. **Implement in two phases** -- Phase 1: build script + `apiFetch` wiring + a few validated endpoints as proof. Phase 2: wire remaining endpoints, remove `isKnownMapKey` guards, optionally migrate WS to precompiled.
